# The Graphify output contract is the gate; the running version is probed once, reported, and never fatal

ADR-0003 pins Graphify to an exact version, but only as an install-time instruction. OSG-009 fixed the `graphify path` **text** contract empirically against **0.9.91**, and `queryPath` parses that stdout because the exit code is `0` for both "found" and "no path". Nothing in osgraph recorded or checked which binary actually produced an answer: `OSGRAPH_GRAPHIFY_BIN` defaults to the bare name `"graphify"` (`src/config.ts`), resolved by PATH order in `resolveExecutable` (`src/graphify/resolve.ts`), and the only mention of a version anywhere in the spawn path was the `GRAPHIFY_NOT_FOUND` message telling the user to "install the pinned version". On this dev machine (2026-10-30) **three** `graphify.exe` sit on PATH — `…Python311\Scripts` → `0.9.91` (the pinned one, winning purely by PATH order), `C:\Users\LENOVO\.local\bin` → `0.8.49`, `…Python312\Scripts` → `0.9.45` — so the pinned binary is selected by accident, not by configuration.

A three-version differential was run (2026-10-30, read-only `--version` and `path` only, `GRAPHIFY_NO_AUTO_REFRESH=1`, against `tests/fixtures/synthetic/graph-osg009.json`) and it reframes the risk:

| case | 0.8.49 | 0.9.45 | 0.9.91 |
|---|---|---|---|
| found (2 hops) | `Shortest path (2 hops):` + `LoginScreen --calls [EXTRACTED]--> AuthenticateUser --references [EXTRACTED]--> User`, exit 0 | identical | identical |
| no path | `No path found between 'A' and 'B'.` | `No directed path found … Re-run with --undirected …` | same as 0.9.45 |
| unknown node | `No node matching 'X' found.` on **stderr**, exit **1** | same text, exit **1** | same text, exit **4** |
| `--version` | `graphify 0.8.49` on stdout, exit 0 | likewise | likewise |

`path.ts` already absorbs both differences by accident of being written defensively: `NO_PATH_RE`'s `(?:directed |undirected )?` group is optional, and the unknown-node branch is a disjunction (`exit === 4 || /No node matching/` over stdout+stderr). The premised failure — a real path reported as `found: false` — **did not reproduce on any version present on this machine**. What the differential did expose is a different, real silent-wrong-answer hole, in `parsePathLine`: if a future version changes the ` --rel [CONF]--> ` arrow syntax while keeping the `Shortest path (N hops):` header, `SHORTEST_RE` still matches, `hops` still parses, and `queryPath` returns `found: true` with a single step whose `label` is the entire line. The same applies when a found header is followed by no path line at all (today: `found: true, path: []`). That is the failure mode worth spending code on — not the version number.

Decision — option **(e) as the gate, option (c) as the record**:

- **The output contract is the only thing that can fail a call.** `parseGraphifyPathOutput` additionally requires the found case to be internally consistent: `hops >= 1`, `steps.length === hops + 1`, every label non-empty, and every step after the first carrying a non-empty `relation` and `confidence`. Any inconsistency returns `undefined` exactly as unrecognised text does, so `runGraphifyPath` throws the **existing `GRAPHIFY_FAILED`** (message widened to "…matched neither 'Shortest path' nor 'No path found', or did not parse as a consistent path"). **No new `OsgraphErrorCode` is introduced** by this ADR.
- **The version is probed once per process and is never fatal.** Immediately before the first `graphify path` spawn in a process, osgraph runs `<resolved exe> --version` once and memoizes the result **keyed by the resolved absolute path** (so a changed `OSGRAPH_GRAPHIFY_BIN` or PATH re-probes, and the probe and the query always describe the same file). The probe reads **stdout**, matching `/^graphify\s+(\d+\.\d+\.\d+\S*)/m` — confirmed on all three versions above. A failed, non-zero or unparseable probe is also not fatal: the version is recorded as `null`.
- **Mismatch warns on two channels.** One `ctx.log` stderr line per process, and `queryPath`'s result always carries `graphifyVersion: string | null` plus, only on mismatch, `graphifyVersionWarning: string` naming both the observed and the pinned version and pointing at `OSGRAPH_GRAPHIFY_BIN`. The field lives on `QueryPathResult`, **not** on `ToolResponse`/`graphCompleteness`: `queryPath` is the only tool that spawns (OSG-007), and `rebuild`/`queryImpact`/`listViolations` must not grow a field they can never populate.
- **The pin stays where it already is, in code.** `GRAPHIFY_VERSION = "0.9.91"` in `src/graph/types.ts` *is* the pin — it is already written into every snapshot as `graph.graphify_version`. The probe compares against that same constant. Not `package.json` (a custom field means runtime path-resolution from `dist/` and a second copy that drifts from the snapshot field), and deliberately **not** a config key or env var: a configurable pin is one a user silences instead of fixes.
- **ADR-0003's guard widens to a two-entry allow-list.** `assertSafeGraphifyArgs` today rejects any `argv[0] !== "path"`, which would reject the probe. It now permits exactly `path` and `--version`; anything else — `install` and `hook` emphatically included — still throws `GRAPHIFY_FAILED` before any spawn. `--version` is read-only, was already exercised under OSG-009, and the probe sets `GRAPHIFY_NO_AUTO_REFRESH=1` like every other graphify spawn.
- **Nothing else in `path.ts` changes.** `NO_PATH_RE`, `NO_NODE_RE`, the exit-4-or-message unknown-node branch, `UNKNOWN_NODE`, `GRAPHIFY_NOT_FOUND` and `GRAPHIFY_FAILED` all stay as written — the differential shows they are already the version-tolerant part. One observed gap is left alone on purpose: `from` and `to` resolving to the same node exits **3** with the message on stderr, so it surfaces as `GRAPHIFY_FAILED`; loud and rare, not worth its own code in v1.

**Measured cost** (2026-10-30, this machine). `graphify --version`: mean **214 ms** over 10 runs (min 184, max 284 on the cold first run) on 0.9.91, 154 ms on 0.8.49. `graphify path` against the 4-node OSG-009 fixture: mean **350 ms** over 5 runs. The probe therefore costs one extra ≈0.21 s on the first `queryPath` of a process and exactly zero on every call after it — about +61% on that first call, 0% thereafter, inside a server whose `rebuild` is already seconds-to-minutes of strictly serialized servicestudio calls (ADR-0007). Accepted. A per-call probe would have been a flat +61% forever and was never a candidate at that ratio.

Rejected alternatives:

- **(a) README-only, no code.** Keeps the hazard invisible after the fact: the verifier cannot tell which binary produced a snapshot's answers, and the `parsePathLine` hole stays open. The README text is kept as *part* of this decision, not instead of it.
- **(b) fail with a dedicated error code on any non-pinned version.** A false-negative machine: 0.9.45 produces byte-identical output for every case `queryPath` parses, and 0.8.49 differs only where the parser is already tolerant — failing either would make osgraph unusable on a machine that answers correctly, and turn a PATH-ordering accident into a hard outage for a read-only query tool. OSG-005 also ships by git-install and `npm pack` tarball, neither of which can install or select a Python console script for the user.
- **(d) a pinned range or minimum with a compatibility rule.** A compatibility rule needs a changelog. `graphifyy` is a GitHub-only distribution with no PyPI release history, and the differential shows its breaking changes land in text wording and exit codes, which its version numbers demonstrably do not signal (0.8→0.9 changed the no-path wording; 0.9.45→0.9.91 changed an exit code). A range would encode a guarantee upstream does not make.
- **Reading the version from the snapshot's `graph.graphify_version` instead of spawning.** That field is osgraph's own written constant — evidence of what osgraph believes, never of which binary ran.

README (slice S7) must state, under `OSGRAPH_GRAPHIFY_BIN`: the default is the bare name `"graphify"`, resolved by **PATH order, which is not a pin**; setting it to the **absolute path** of the pinned executable is strongly recommended, because a machine with several Python script directories on PATH can easily carry more than one `graphify` (this dev machine carries three); `where graphify` / `which -a graphify` is the one-liner to check; the pinned version is **0.9.91**, installed per ADR-0003 with `pip install git+https://github.com/Graphify-Labs/graphify.git` and **never** `graphify install` or `graphify hook install`; and every `queryPath` result reports the version it actually ran, with a warning on mismatch — so the warning is the thing to act on, not a silent hazard to fear.

Live-verification open points:

- With the default bare `graphify`, confirm the probe reports `0.9.91` and no warning; then point `OSGRAPH_GRAPHIFY_BIN` at `C:\Users\LENOVO\.local\bin\graphify.exe` (0.8.49) and confirm the warning fires, `graphifyVersion` is `"0.8.49"`, **and** found / no-path / unknown-node all still answer correctly (the differential predicts they will — if they do not, this ADR's "warn, never fail" balance must be revisited).
- Confirm the new consistency check does not false-positive on a real multi-hop path (hops ≥ 3) from the `demoportal` scope snapshot; the fixture only exercises 1 and 2 hops.
- Confirm on any non-Windows machine that `graphify --version` still writes to **stdout**; a build that writes it to stderr yields `graphifyVersion: null`, which must stay non-fatal.
- Re-run the three-version differential and record it in `osgraph/tests/live/demoportal-scope.md` if a fourth `graphify` ever appears on PATH, or whenever the pin is moved off 0.9.91.
